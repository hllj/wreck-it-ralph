The loop

How one session runs

A session builds one feature, or a few in parallel. Agents do the work, and gates check it before it counts. Then the next session starts with brand-new contexts and reads the same files.

Fresh context, every time

No agent remembers the previous one. Each starts by reading learnings.md, the progress log and git history, then runs init.sh and a smoke test before touching anything.

Ralph lives inside

A failed feature is retried next session in a new context. The new attempt gets the failure note and is told not to repeat what failed: the Ralph loop, but with a real verifier.

It stops for a reason

The loop stops when everything passes, when the budget or session cap is reached, when it's stuck, or when only work waiting on you is left. Each stop has a code and an entry in last-run.md.

The backlog

Where a feature can be

Every feature in .harness/feature_list.json has one status. Agents can move it only along these arrows, and only through feature-list.sh. The feature's description, steps and tests are locked.

WhoCan doCan never do
coderclaim, ask, propose a split or follow-up, commit codepass a feature, edit the spec
testerpass or fail the claimed features, askpass something nobody claimed, change product code

Scale

Parallel coders

With "parallel": {"max_workers": 2}, a headless session can build features whose tags don't overlap at the same time. Each gets its own git worktree, and a merge gate brings the work back. This is session 2 of the live trial:

Interactive /run stays one step at a time, because subagents can't be pinned to a worktree reliably. A feature without tags never runs in parallel, and a tag every feature shares is ignored.

Testing

Proof you can replay, and gaps you can see

The tester does not just say it works. The contract is a set of locked examples, the tester replays them on the running app and leaves evidence, and coverage shows what no run touched. Three rules: no evidence, no PASS; coverage is visibility, not correctness; agents point at gaps, you decide.

PieceWhat it isWho can change it
ExampleData: input, expect, and how to compare (exact, partial, contains, regex). Never a shell command.Only you, through an approved proposal
REDfeature-list.sh red runs the verify commands and replays the examples; it records RED only if something fails. claim is refused until then.The coder, before implementing
Replayreplay.sh runs examples through an http or cli adapter and writes evidence to .harness/evidence/.A gate script compares; nobody edits results
Verdictreport.sh: pass, fail, blocked (environment, not counted as a failure), inconclusive (asks you).The tester; pass needs complete replay evidence
Gapscoverage.sh gaps lists branches and lines of the diff that never ran; the tester probes each and classifies it, with confidence and evidence.The tester classifies; you decide what becomes an example
BaselineA committed snapshot of coverage. The ratchet fails if it drops, for the whole repo and for each changed file.Only you, between sessions
 
/wreck-it-ralph:demo F002 --run                  # replay every example on the running app
/wreck-it-ralph:demo F002 --example EX002        # one example; --step N or --from A --to B for a slice
/wreck-it-ralph:example F002 "price below zero is rejected"   # proposes a new locked example for you to approve
.harness/coverage.sh run --id F002 && .harness/coverage.sh gaps F002
.harness/coverage.sh baseline                     # you record it; then: .harness/coverage.sh ratchet

Coverage reads Python (coverage.py), Node (vitest, jest, c8, nyc) and Go. Go has no branch data, so branches show as n/a, never 0%. The changed-file report is labelled as such: it is not coverage of the feature. Set "coverage": {"mode": "gate"} to make a drop fail the features passed in that session.

This is a pre-release. It has run once end to end on a small Python API, where the tester caught a crash the examples did not cover. Replay has no Playwright adapter yet, and mutation testing is not built. See the README, "Known limits".

Quickstart

From empty folder to first passing feature

You need git with user.name and user.email set, and jq. All commands are typed in Claude Code unless shown as a shell command.

  1. Load the plugin

    Try it from a local checkout, or install it from your marketplace.

    claude --plugin-dir /path/to/wreck-it-ralph

  2. Describe the goal

    The initializer turns it into a locked feature list with tests, plus init.sh and a progress log, then commits. For an existing codebase add --brownfield; for a non-web project pick a preset.

    /wreck-it-ralph:init "Python CLI textstats: words, lines, top N words" --preset cli

  3. Run the loop and watch

    This session orchestrates fresh coder and tester subagents. It prints one line per session, and you can interrupt at any time; all state is on disk.

    /wreck-it-ralph:run --max-sessions 5

  4. Add features whenever you like

    The planner breaks the request into small, testable features and files a proposal. You see every test command it will run before you approve.

    /wreck-it-ralph:add "Export the top-N list as CSV"
/wreck-it-ralph:backlog approve P001

  5. Answer when it asks

    A feature that needs a decision, or has failed three times, waits for you while the loop carries on with the others.

    /wreck-it-ralph:backlog questions
/wreck-it-ralph:backlog answer F005 "exit code 2 for usage errors"

  6. Check how it's going

    status shows progress, spend, questions and proposals. doctor checks the setup and whether every plugin the pipeline uses is installed.

    /wreck-it-ralph:status
/wreck-it-ralph:doctor

One small task? Skip the harness and use the in-session Ralph loop. It repeats the same prompt until the check command passes, so "I'm done" alone isn't enough to stop it.

/wreck-it-ralph:ralph "Make the test suite green" --verify 'npm test' --max-iterations 15
Unattended

Run it without you, in stages

Earn trust in a loop step by step. Start with shadow runs and read the reports. Move up a level once they keep being right.

LevelWhere the work goesYour branch
L1 shadowharness/shadow-* branch, then back to yours; only a report is leftuntouched
L2 assistedharness/run-* branch; optional push and pull requestuntouched
L3 unattendedcommits on the current branchcommits land here

Set a budget before any unattended run. It applies per run and is checked before every session. 0 means no limit.

"budget": { "max_cost_usd": 10, "max_wall_minutes": 240, "max_diff_lines": 800, "on_large_diff": "stop" },
"parallel": { "max_workers": 2 },
"escalate_after_failures": 3
/wreck-it-ralph:run-headless --rollout L1 --max-sessions 3
/wreck-it-ralph:trigger cron --every 2h          # prints a crontab line; you install it
/wreck-it-ralph:trigger github --on-failure "CI" --rollout L2
/wreck-it-ralph:setup --notify                   # desktop notice when it needs you

Reference

What lives in .harness/

feature_list.json
The backlog and the source of truth. Statuses change only through feature-list.sh; the spec is locked.
proposals.json
Changes to the backlog that wait for your approval.
learnings.md
Short lessons written by the curator: commands that work, conventions, what failed. Every agent reads it first.
progress.md
One entry per agent per session. Older entries move to progress/.
init.sh · stop.sh
Start the app and smoke-test it at the beginning of every session; stop servers when a run ends.
config.json
Pipeline, budgets, rollout, parallel workers, hooks. Anything that can run commands needs /wreck-it-ralph:trust.
ledger.jsonl · events.jsonl
Spend per agent run; every gate step as an event other tools and hooks can read.
evidence/ · coverage/
Replay results and verdict reports per feature; normalized coverage, gap reports and the ratchet. Git-ignored, except coverage/baseline.json, which you commit.
last-run.md · sessions/
The summary of the last run, plus per-agent and per-test logs.
