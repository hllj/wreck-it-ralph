# wreck-it-ralph-loop

Two tools in one Claude Code plugin:

1. **Ralph Loop** (`/wreck-it-ralph-loop:ralph-loop`): the original in-session Stop-hook loop (documented further below).
2. **Long-running harness**: an implementation of the ideas in Anthropic's
   [Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents).
   Every session runs in a **fresh context**; all state lives on disk and in git.

## Install

```
/plugin install wreck-it-ralph-loop --marketplace <owner>/<repo>
```

(replace `<owner>/<repo>` with the marketplace that hosts this plugin), or try it locally with `claude --plugin-dir /path/to/wreck-it-ralph`. Requires `bash`, `git` (with `user.name`/`user.email` set) and `jq`; macOS and Linux only.

## Harness quick start

```bash
/wreck-it-ralph-loop:harness-init "Build a todo web app with auth, lists, and drag-and-drop"
/wreck-it-ralph-loop:harness-run            # interactive: fresh-context subagents in this session
/wreck-it-ralph-loop:harness-run-headless   # unattended: separate `claude -p` processes (or .harness/run.sh)
/wreck-it-ralph-loop:harness-status
/wreck-it-ralph-loop:harness-cancel         # stops after the current session
```

### Setup command

`/wreck-it-ralph-loop:harness-setup [--preset web|cli|none] [--max-sessions N] [--no-browser] [--check] [--force]` creates or repairs the scaffold without running the initializer: prerequisite check, config for the preset (`web` = coder -> tester + Playwright MCP, `cli` = coder -> tester, `none` = coder only), wrappers, and merged `.gitignore` entries (`.playwright-mcp/`, `node_modules/`, `.env*`, keys, logs, ...). It is safe to re-run and never overwrites your config unless `--force`. `harness-init` calls it for you. For the `web` preset, start Claude Code with `--mcp-config .harness/mcp.json` so subagents get the browser tools.

### Safety model

- **Your work is protected.** Harness commits use `git add -A`, so `harness-init` refuses to start in a git project with uncommitted changes (use `--branch NAME` to work on a separate branch, or `--allow-dirty` if you really want them included). Starting a loop is also refused on a dirty tree unless `allow_dirty` is set in `.harness/config.json`. Changes under `.harness/` don't count.
- **Trust.** `.harness/config.json` (`permission_mode`, `allowed_tools`, `final_verify_command`, `claude_bin`, `model`), the MCP config and custom agents in `.harness/agents/` come from the repository and can run commands. A loop refuses to start until you review them with `/wreck-it-ralph-loop:harness-trust` (recorded locally in the git-ignored `.harness/.trusted`; any change to those settings requires re-trusting). Configs generated by `harness-setup` itself are trusted automatically.
- **Headless permissions.** The default `permission_mode` is `acceptEdits` with an explicit `allowed_tools` list (including `Bash`); the runner prints a warning when you switch to `bypassPermissions`. Use a sandbox or throwaway checkout for unattended runs.
- **The tester is rigorous.** It reads the coder's "Known issues", probes inputs beyond the listed steps, and fails a feature whose known issue or probe contradicts its description; the coder must not claim a feature it knows is incomplete.
- **The tester is independent.** The coder may only `claim`; at the end of every session the gate resets any feature that became passing without being claimed when the tester started.
- **One loop per project.** `begin --new-run` takes a heartbeat lock (a headless runner also registers its pid). A second loop stops with code 7; clear a stale lock with `.harness/step.sh unlock`.
- **Commit safety.** Starting a loop requires a configured git identity (stop code 6). Commit failures are reported (`WARN=`) instead of swallowed, and committing files over 5 MB prints a warning. Language-specific ignore sets (`dist/`, `.venv/`, `target/`, ...) are added to `.gitignore` at setup, at finalize, and re-detected at every loop start. The `.harness/*.sh` wrappers (machine-specific paths) are git-ignored and untracked automatically.
- **Wrappers self-heal.** `.harness/*.sh` find the plugin through `$CLAUDE_PLUGIN_ROOT`, the recorded path, or the newest installed copy, and `harness-run` refreshes them on start (`harness-setup --refresh` does it manually).

### How it works

| Piece | Role |
|---|---|
| **initializer agent** (`agents/initializer.md`) | Runs once. Writes `feature_list.json` (all `passes:false`), `init.sh`, `progress.md`, makes the first commit. Implements nothing. |
| **coder agent** (`agents/coder.md`) | One feature per session. Startup routine: `pwd`, read progress + git log, pick next failing feature, run `init.sh` + smoke test (fix breakage first), implement, self-check, **claim**, commit, log progress, leave a clean tree. |
| **tester agent** (`agents/tester.md`) | Independent verifier. Exercises each feature's `steps` end to end through the Playwright MCP browser and is the only role that marks a feature `passes:true`. |
| **user-defined agents** | Drop `.harness/agents/<name>.md` (templates in `templates/agents/`: `reviewer`, `cleaner`) and add them to the pipeline in `.harness/config.json`. |
| **feature list** | `.harness/feature_list.json`. Agents change status only via `.harness/feature-list.sh claim\|pass\|fail`. The spec is hashed at init; if an agent edits it the runner restores it. |
| **progress file + git** | `.harness/progress.md` + commit per feature. The runner auto-commits anything left uncommitted so the next session starts clean. |
| **init.sh** | Starts the app and runs a smoke test; run at the start of every session. |
| **gates** (`scripts/harness-step.sh`, `.harness/step.sh`) | Deterministic rules shared by both loop modes: `begin` (STOP flag, session cap, stuck check, final verification, picks the target feature), `task`/`plan`/`spawn-info` (what to run), `end` (spec-lock restore, clean tree, stuck detection), `summary`. |
| **interactive loop** (`/harness-run`) | The main Claude Code session is a thin **orchestrator**: per session it spawns a fresh `coder` subagent, then a fresh `tester` subagent (plus any custom agents), calling the gates between steps. Uses your session's login, permissions and MCP servers, and you can watch or interrupt. Subagents cannot spawn subagents, so the pipeline is flat. |
| **headless loop** (`.harness/run.sh`) | Same gates, but each agent is a separate `claude -p` process, for overnight/CI runs. Needs a valid login and defaults to `bypassPermissions`. |

Both modes stop when all features pass (and `final_verify_command`, if set, succeeds), on the `STOP` flag, at `max_sessions`, or when `stuck_limit` sessions pass with no new passing feature. They share all state in `.harness/`, so you can switch modes mid-project.

### Configuration (`.harness/config.json`)

```json
{
  "max_sessions": 100,
  "stuck_limit": 3,
  "permission_mode": "acceptEdits",
  "mcp_config": ".harness/mcp.json",
  "final_verify_command": "npm test",
  "pipeline": [
    { "agent": "coder",    "blocking": true },
    { "agent": "tester",   "blocking": true, "when": "claimed" },
    { "agent": "reviewer", "blocking": false, "every": 5 }
  ]
}
```

Pipeline step fields: `agent` (looked up in `.harness/agents/`, then the plugin's `agents/`, then `templates/agents/`), `blocking`, `every` (run every N sessions), `when` (`always` | `claimed` | `failing`).
If the pipeline has no `tester`, coder claims are accepted as passes.

> ⚠️ Headless runs execute shell commands unattended. The default is `acceptEdits` with an explicit tool list; `bypassPermissions` removes all prompts. Run in a sandbox/VM or throwaway checkout.

Browser testing uses the Playwright MCP server from `.harness/mcp.json` (`npx @playwright/mcp@latest`). Swap in any other browser MCP you prefer.

### Logs and run summary
- Headless mode writes each agent's output to `.harness/sessions/NNN-<agent>.log`.
- When a loop stops for any reason it prints a summary (stop reason, features, commits this run) and saves it to `.harness/last-run.md`.
- `.harness/progress.md` is the human-readable narrative of every session.
- Interactive mode appends one line per agent outcome to `.harness/sessions/NNN-notes.md` (via `step.sh note`), included in the summary.

Run the script tests with `bash tests/run-tests.sh` (uses a fake `claude`).

## Ralph Loop (in-session)

Implementation of the Ralph Wiggum technique for iterative, self-referential AI development loops in Claude Code.

## What is Ralph Loop?

Ralph Loop is a development methodology based on continuous AI agent loops. As Geoffrey Huntley describes it: **"Ralph is a Bash loop"** - a simple `while true` that repeatedly feeds an AI agent a prompt file, allowing it to iteratively improve its work until completion.

This technique is inspired by the Ralph Wiggum coding technique (named after the character from The Simpsons), embodying the philosophy of persistent iteration despite setbacks.

### Core Concept

This plugin implements Ralph using a **Stop hook** that intercepts Claude's exit attempts:

```bash
# You run ONCE:
/wreck-it-ralph-loop:ralph-loop "Your task description" --completion-promise "DONE"

# Then Claude Code automatically:
# 1. Works on the task
# 2. Tries to exit
# 3. Stop hook blocks exit
# 4. Stop hook feeds the SAME prompt back
# 5. Repeat until completion
```

The loop happens **inside your current session** - you don't need external bash loops. The Stop hook in `hooks/stop-hook.sh` creates the self-referential feedback loop by blocking normal session exit.

This creates a **self-referential feedback loop** where:
- The prompt never changes between iterations
- Claude's previous work persists in files
- Each iteration sees modified files and git history
- Claude autonomously improves by reading its own past work in files

## Quick Start

```bash
/wreck-it-ralph-loop:ralph-loop "Build a REST API for todos. Requirements: CRUD operations, input validation, tests. Output <promise>COMPLETE</promise> when done." --completion-promise "COMPLETE" --max-iterations 50
```

Claude will:
- Implement the API iteratively
- Run tests and see failures
- Fix bugs based on test output
- Iterate until all requirements met
- Output the completion promise when done

## Commands

### /ralph-loop

Start a Ralph loop in your current session.

**Usage:**
```bash
/wreck-it-ralph-loop:ralph-loop "<prompt>" --max-iterations <n> --completion-promise "<text>"
```

**Options:**
- `--max-iterations <n>` - Stop after N iterations (default: unlimited)
- `--completion-promise <text>` - Phrase that signals completion

### /cancel-ralph

Cancel the active Ralph loop.

**Usage:**
```bash
/cancel-ralph
```

## Prompt Writing Best Practices

### 1. Clear Completion Criteria

❌ Bad: "Build a todo API and make it good."

✅ Good:
```markdown
Build a REST API for todos.

When complete:
- All CRUD endpoints working
- Input validation in place
- Tests passing (coverage > 80%)
- README with API docs
- Output: <promise>COMPLETE</promise>
```

### 2. Incremental Goals

❌ Bad: "Create a complete e-commerce platform."

✅ Good:
```markdown
Phase 1: User authentication (JWT, tests)
Phase 2: Product catalog (list/search, tests)
Phase 3: Shopping cart (add/remove, tests)

Output <promise>COMPLETE</promise> when all phases done.
```

### 3. Self-Correction

❌ Bad: "Write code for feature X."

✅ Good:
```markdown
Implement feature X following TDD:
1. Write failing tests
2. Implement feature
3. Run tests
4. If any fail, debug and fix
5. Refactor if needed
6. Repeat until all green
7. Output: <promise>COMPLETE</promise>
```

### 4. Escape Hatches

Always use `--max-iterations` as a safety net to prevent infinite loops on impossible tasks:

```bash
# Recommended: Always set a reasonable iteration limit
/wreck-it-ralph-loop:ralph-loop "Try to implement feature X" --max-iterations 20

# In your prompt, include what to do if stuck:
# "After 15 iterations, if not complete:
#  - Document what's blocking progress
#  - List what was attempted
#  - Suggest alternative approaches"
```

**Note**: The `--completion-promise` uses exact string matching, so you cannot use it for multiple completion conditions (like "SUCCESS" vs "BLOCKED"). Always rely on `--max-iterations` as your primary safety mechanism.

## Philosophy

Ralph embodies several key principles:

### 1. Iteration > Perfection
Don't aim for perfect on first try. Let the loop refine the work.

### 2. Failures Are Data
"Deterministically bad" means failures are predictable and informative. Use them to tune prompts.

### 3. Operator Skill Matters
Success depends on writing good prompts, not just having a good model.

### 4. Persistence Wins
Keep trying until success. The loop handles retry logic automatically.

## When to Use Ralph

**Good for:**
- Well-defined tasks with clear success criteria
- Tasks requiring iteration and refinement (e.g., getting tests to pass)
- Greenfield projects where you can walk away
- Tasks with automatic verification (tests, linters)

**Not good for:**
- Tasks requiring human judgment or design decisions
- One-shot operations
- Tasks with unclear success criteria
- Production debugging (use targeted debugging instead)

## Windows Compatibility

The stop hook uses a bash script that requires Git for Windows to run properly.

**Issue**: On Windows, the `bash` command may resolve to WSL bash (often misconfigured) instead of Git Bash, causing the hook to fail with errors like:
- `wsl: Unknown key 'automount.crossDistro'`
- `execvpe(/bin/bash) failed: No such file or directory`

**Workaround**: Edit the cached plugin's `hooks/hooks.json` to use Git Bash explicitly:

```json
"command": "\"C:/Program Files/Git/bin/bash.exe\" ${CLAUDE_PLUGIN_ROOT}/hooks/stop-hook.sh"
```

**Location**: `~/.claude/plugins/cache/claude-plugins-official/ralph-wiggum/<hash>/hooks/hooks.json`

**Note**: Use `Git/bin/bash.exe` (the wrapper with proper PATH), not `Git/usr/bin/bash.exe` (raw MinGW bash without utilities in PATH).
